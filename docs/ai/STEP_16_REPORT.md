## Architecture and final chat contract

MongoDB is permanent authority for members, yachts, brokerProfiles, crewProfiles, destinations, offices, articles, wishlistItems, yachtInquiries, sellYachtRequests, conversations and messages, including counters/history. Redis owns popularity caches, atomic quotas, temporary TTL state, session presence/typing and Socket.IO pub/sub. GraphQL serves persistent application APIs. Socket.IO serves authenticated private realtime communication. Batch is idle and Redis-independent.

Customer → specific public Yacht → assigned BrokerProfile → preserved brokerMemberId → private Conversation. brokerMemberId is immutable and is never recomputed for history authorization. Current assignment/profile link changes do not transfer private history. The accepted unique relationship is customerId/yachtId/brokerId, not a replacement four-field key: a same-profile relink reuses the old historical conversation; a different assigned profile creates a new relationship. This behavior is explicitly tested and retains the existing index/schema contract. ADMIN may inspect explicit GraphQL history, cannot send/join/type/mark recipient reads, and receives null unreadCount even if a historical participant is promoted. No global chat or owner-chat redesign.

New starts require PUBLISHED Yacht, active assigned profile and an ACTIVE non-ADMIN linked broker Member; clients cannot supply broker identity. Existing history remains available to ACTIVE historical participants after hiding/removing the yacht/profile or removing/relinking the broker link. No history is deleted. Deleted/blocked/missing Members cannot authenticate. Mongo persistence is independent of realtime delivery; clients recover missed messages through history and explicitly reauthenticate/rejoin after reconnect.

## Safe reconciliation runbook

Do not execute automatically. In a separately authorized operator session, explicitly set the target MONGODB_URI and first run the no-flag utility with read-only database credentials. Inspect mismatch/orphan output, deployed relation uniqueness and the target database/version. The script does not load local .env, automatically create collections/indexes, or delete malformed/orphan relations.

Apply requires --apply --writes-paused. Drain API traffic/in-flight cache fills, pause all wishlist/external writers for the entire scan/repair, and hold maintenance until existing 30s popularity pages expire after repair. The acknowledgment does not enforce a distributed lock. A changed relation count or observed counter skips the write; conflicts return exit 2. Only likesCount is set; timestamps/business data/history remain intact. No cross-document transaction exists, so operational quiescence is mandatory; retries begin with a fresh dry-run. Historical relations linked to blocked/deleted Members remain relations under the existing source-of-truth contract. No actual utility database invocation occurred here.
